# Наблюдаемость и нагрузочное тестирование

## Запуск

`make run` запускает локальное приложение вместе с Prometheus, Grafana, Alertmanager, Node Exporter и TCP-проверками. Grafana доступна на http://localhost:3000, Prometheus — на http://localhost:9090. Порты привязаны к localhost. Локальные имя/пароль по умолчанию: `admin` / `snapflow-local-admin`; измените `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD` в `.env`. Grafana использует эти значения при первом создании пользователя: существующий пароль в сохранённом томе автоматически не меняется.

В production переменная `GRAFANA_ADMIN_PASSWORD` обязательна и должна быть уникальной. Для удалённого доступа используйте SSH-туннель или защищённый HTTPS-прокси с аутентификацией. Переменные `GRAFANA_PORT` и `PROMETHEUS_PORT` меняют локальные порты. В production deploy использует дополнительные Compose-файлы; конфигурация копируется вместе с релизом. Фактическое развёртывание после изменения pipeline необходимо проверить отдельно.

## Дашборды

В папке Grafana `SnapFlow` находятся:

- `SnapFlow overview`: CPU, размер изображений в хранилище, очереди, RPS, HTTP p95, среднее, минимум и максимум HTTP и SQL за выбранный период.
- Готовый [Node Exporter Full, dashboard 1860 revision 37](https://grafana.com/grafana/dashboards/1860-node-exporter-full/).
- Готовый [RabbitMQ Overview, dashboard 10991 revision 10](https://grafana.com/grafana/dashboards/10991-rabbitmq-overview/).

Панель `Image storage used` показывает сумму размеров зашифрованных оригиналов, превью и временных staging-файлов. Рядом есть разбивка по этим категориям. Для локального хранилища суммируются размеры обычных файлов в `private/uploads`, `private/thumbnails` и `private/staging`, включая временные файлы записи; размеры plaintext, служебные данные PostgreSQL и другие файлы не входят. Это сумма байтов файлов, а не число блоков, выделенных файловой системой. Локальный обход выполняется в фоне раз в 30 секунд; изменения во время обхода могут отразиться при следующем измерении.

Для S3 те же категории подсчитываются по размерам объектов соответствующих префиксов в текущем бакете раз в пять минут. Нужны права `s3:ListBucket`; большое количество объектов увеличивает время сканирования, количество запросов и потенциальные затраты. Учитываются только текущие версии объектов, без предыдущих версий и незавершённых multipart-загрузок. Сканирование ограничено двумя минутами. При ошибке панель не показывает старое значение как актуальное; состояние доступно в `snapflow_image_storage_scan_success`. Реальный S3-провайдер для этой метрики отдельно не проверялся.

CPU и метрики файловой системы Node Exporter относятся к Linux-хосту. В Docker Desktop это Linux VM, а не показатели Windows в целом. Системный алерт свободного места по-прежнему следит за файловой системой и не является размером изображений. RabbitMQ предоставляет метрики через свой плагин; статистика по отдельным очередям собирается из `/metrics/detailed`. В отдельных панелях сторонних шаблонов могут потребоваться дополнительные экспортёры или метки.

HTTP группируется по методу, шаблону маршрута и коду ответа, без идентификаторов запросов и конкретных URL. P95 — оценка по корзинам гистограммы, не точное значение. Среднее за период рассчитывается по изменению суммы длительностей и числа запросов. Минимум/максимум собираются за интервалы между опросами Prometheus (15 секунд); `min_over_time`/`max_over_time` выбирает экстремумы в указанном диапазоне. На границах периода возможна погрешность до одного интервала, а при пропуске опросов эти значения не гарантированы. Запросы, выполнявшиеся вне периодов работы сборщика или потерянные при перезапуске процесса, не учтены.

SQL измеряется для запросов GORM приложения (соединения мигратора не охвачены). Панели показывают автоматически определённую вызывающую функцию и query_id; каталог SQL query catalog внизу дашборда содержит соответствующие шаблоны, без ручной настройки Grafana. Имя — техническое имя функции, разбитое на слова: оно может измениться при рефакторинге и не всегда равно бизнес-операции; одна функция может выполнять несколько запросов. SQL-шаблоны берутся из GORM до подстановки параметров. Числовые литералы скрываются; запросы со строковыми литералами, комментариями, обратными косыми чертами или dollar-quoted строками целиком скрываются как небезопасные. Идентификаторы таблиц и колонок показываются: не включайте в них пользовательские или секретные данные. Prometheus хранит каталог как отдельную метрику snapflow_sql_query_info, доступ к метрикам и Grafana нужно ограничивать. Каталог ограничен 300 сочетаниями функции и отпечатка на процесс; остальные операции объединяются в other и шаблон для них не сохраняется. После перезапуска каталог заново заполняется выполняющимися запросами; история в Prometheus живёт согласно retention. Переменное число аргументов IN создаёт разные шаблоны. Метрики охватывают сервер, worker и outbox. Старые временные ряды без метки operation постепенно исчезнут по retention. Отпечаток известного шаблона можно вычислить: echo 'SELECT ...' | go run ./cmd/sql-fingerprint.

## Telegram и алерты

В `.env` задайте:

```dotenv
TELEGRAM_BOT_TOKEN=токен_бота
TELEGRAM_CHAT_ID=числовой_id_чата
```

Создайте бота через BotFather, начните с ним диалог или добавьте в нужную группу и получите chat ID через Telegram Bot API. Не публикуйте токен и не помещайте его в репозиторий. Без обоих значений bridge запускается с отключённой доставкой: алерты остаются видимыми в Prometheus/Alertmanager, но в Telegram не отправляются.

Prometheus оценивает правила из `monitoring/prometheus/alerts.yml`; Alertmanager группирует сообщения и асинхронно передаёт их мосту, который отправляет сообщения и возвращает ошибку Alertmanager при сбое Telegram для повторных попыток. Оповещения и восстановление отправляются для недоступности метрик приложения и RabbitMQ, неуспешного TCP-подключения к PostgreSQL/Redis, ошибок приложения, большого процента HTTP 5xx, роста очередей и parking, недостатка места и высокой загрузки CPU. TCP-проверка не доказывает корректность авторизации или SQL-запросов. Доступность Alertmanager и моста также проверяется по TCP, но Prometheus, Alertmanager и мост в этом стенде одиночные: их собственная недоступность может препятствовать оповещению.

Пороговые значения и время срабатывания изменяются в `monitoring/prometheus/alerts.yml`, интервалы группировки и повтора — в `monitoring/alertmanager/alertmanager.yml`. После изменения перезапустите сервисы `prometheus` и/или `alertmanager` через Compose. Токен и ID считываются при старте `alertbridge`, после изменения `.env` пересоздайте сервис. Alertmanager не обеспечивает бесконечную доставку при длительных сбоях; при длительной недоступности Telegram проверьте его состояние и логи bridge. Настоящая доставка зависит от доступа к Telegram API и разрешений бота в чате.

## k6

`make load` запускает k6 в контейнере против локального `server` после `make run`. По умолчанию сценарий только читает публичный `/`; задайте `K6_TOKEN` от отдельного тестового пользователя в `.env`, чтобы вместо этого тестировать авторизованный список `/api/images`. Нагрузку можно изменить через `K6_VUS` (по умолчанию 5) и `K6_DURATION` (по умолчанию 30s). Порог p95 < 1 секунды и доля ошибок < 1% — стартовые ориентиры, не подтверждённые SLO.

Альтернативные имена этих команд: `make k6` и `make k6-upload`.

`make load-upload` отдельно запускает изменяющий данные сценарий: он загружает тестовый PNG, ждёт обработки, ищет полученное изображение и ставит его на удаление. Для него обязателен `K6_TOKEN` выделенного тестового пользователя; число VU задаётся как `make load-upload K6_UPLOAD_VUS=1`. Тест рассчитан только на изолированный стенд. При тайм-ауте, большом числе параллельных загрузок или ошибке очистка может не выполниться; после теста проверьте и удалите оставшиеся тестовые изображения. Сценарий не удаляет посторонние изображения.

Результаты выводятся в консоль и направляются в Prometheus через экспериментальный k6 remote write. При использовании без токена проверяется только публичный endpoint, а не вся бизнес-цепочка. Тесты производительности запускайте на изолированном стенде, не направляйте нагрузку на production без отдельного согласования. На одном компьютере k6 и сервер конкурируют за CPU и диск; результаты не являются замерами производственного окружения.
