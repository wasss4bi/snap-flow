# Snap Flow: CI/CD и production

## Ветки и проверки

Создайте репозиторий на GitHub и ветки `stage` и `prod`. Рабочие ветки называются `feature/<название>`. Workflow запускается для PR в `stage` и `prod`, а также после обновления этих веток. Обычный push в `feature/*` проверок не запускает.

PR `feature/*` → `stage` и PR `stage` → `prod` проходят Go-тесты с PostgreSQL и RabbitMQ, E2E smoke и сборку образа. После merge тесты и сборка повторяются для результирующего коммита. На `stage` образ публикуется в GHCR, на `prod` также выполняется деплой. Прогон PR не публикует образ; SHA образа PR может отличаться от SHA итогового merge-коммита.

В настройках репозитория самостоятельно защитите `stage` и `prod`: запретите прямой push и force push, потребуйте PR и проверки `Test` и `Build image`. Проверьте, что защита применяется к администраторам и не предусмотрены обходы. Workflow не заменяет эти настройки; их доступность зависит от типа репозитория и тарифа GitHub. Для первоначальной настройки ветки и первого успешного прогона временно создайте правила после первого запуска. Деплой обходит проверки PR, если разрешён прямой push в prod.

## Подготовка сервера

Установите Docker Engine и Compose plugin. Создайте пользователя деплоя с доступом к Docker и каталог, например `/srv/snap-flow`; доступ к Docker фактически даёт привилегии root. В каталоге создайте `.env` по образцу `.env.production.example`, ограничьте доступ (`chmod 600 .env`) и заполните все обязательные поля. Не используйте локальные значения секретов. База и очереди сохраняются в Docker volumes, образы хранятся в S3-совместимом бакете. Переменные администратора необходимы каждой миграции; изменение пароля в `.env` не меняет пароль существующего администратора.

Сервер приложения привязан к `127.0.0.1:HTTP_PORT`. Для доступа извне нужен отдельно настроенный HTTPS reverse proxy; настройка домена, TLS и прокси не входит в этот workflow. Укажите в `TRUSTED_PROXIES` только проверенные адреса прокси. Не публикуйте порты PostgreSQL, Redis и RabbitMQ.

## Настройки GitHub

Для environment `production` или репозитория задайте secrets:

* `DEPLOY_HOST`, `DEPLOY_USER` — SSH-хост и пользователь; порт SSH 22.
* `DEPLOY_SSH_KEY` — приватный ключ пользователя деплоя без интерактивной парольной фразы.
* `DEPLOY_KNOWN_HOSTS` — проверенная строка host key из `known_hosts`. Сверьте её отпечаток с сервером по доверенному каналу до добавления.
* `GHCR_READ_USER`, `GHCR_READ_TOKEN` — учётная запись и токен для чтения production-образа из GHCR. Для приватного пакета права на пакет и `read:packages` должны быть настроены отдельно; пакет должен быть доступен этой учётной записи.

Задайте variable `DEPLOY_DIR` — абсолютный путь к каталогу сервера, например `/srv/snap-flow`. Создайте environment `production`, если он поддерживается настройками репозитория. Выдайте GitHub Actions право публиковать пакеты GHCR. Серверу нужны исходящий доступ к GHCR и доступ к S3 и SMTP. Токен чтения GHCR сохраняется Docker на сервере после login; ограничьте его права и защитите Docker config.

## Процесс и ограничения

После успешных проверок GitHub собирает и публикует образ, помеченный SHA коммита. Deploy загружает конфигурацию в `releases/<SHA>`, скачивает образы, поднимает зависимости, запускает миграции и обновляет процессы. После проверки Docker записывает `current-image` и `current-release`. Сервер использует отдельный постоянный `.env`, он не отправляется из GitHub.

Деплой допускает короткий простой. Если миграция прошла, а приложение не запустилось, автоматического отката схемы или контейнеров нет; нужна ручная диагностика. `/` проверяет только ответ HTTP-сервера, а не полную работоспособность S3, почты и очередей. Протестируйте процесс на пустом сервере и проверьте восстановление PostgreSQL и S3 из резервных копий до работы с реальными данными.

Нельзя без плана ротации менять `TWS_SECRET_ACCESS_KEY`: сейчас из него выводится ключ шифрования существующих изображений. Смена секрета может сделать их нечитаемыми. Миграции должны быть совместимы как со старой, так и с новой версией во время развёртывания: старые процессы могут ещё работать при выполнении миграции.
