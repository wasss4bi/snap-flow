# Snap Flow: CI/CD и production

## Ветки и проверки

Создайте репозиторий на GitHub и ветки `stage` и `prod`. Рабочие ветки называются `feature/<название>`. Workflow запускается для PR в `stage` и `prod`, а также после обновления этих веток. Обычный push в `feature/*` проверок не запускает.

PR `feature/*` → `stage` и PR `stage` → `prod` проходят Go-тесты с PostgreSQL и RabbitMQ, E2E smoke и сборку образа. После merge тесты и сборка повторяются для результирующего коммита. На `stage` образ публикуется в GHCR, на `prod` также выполняется деплой. Прогон PR не публикует образ; SHA образа PR может отличаться от SHA итогового merge-коммита.

В настройках репозитория самостоятельно защитите `stage` и `prod`: запретите прямой push и force push, потребуйте PR и проверки `Test` и `Build image`. Проверьте, что защита применяется к администраторам и не предусмотрены обходы. Workflow не заменяет эти настройки; их доступность зависит от типа репозитория и тарифа GitHub. Для первоначальной настройки ветки и первого успешного прогона временно создайте правила после первого запуска. Деплой обходит проверки PR, если разрешён прямой push в prod.

## Подготовка сервера

Установите Docker Engine и Compose plugin. Создайте пользователя деплоя с доступом к Docker и каталог, например `/srv/snap-flow`; доступ к Docker фактически даёт привилегии root. В каталоге создайте `.env` по образцу `.env.production.example`, ограничьте доступ (`chmod 600 .env`) и заполните все обязательные поля. Не используйте локальные значения секретов. База и очереди сохраняются в Docker volumes, образы хранятся в S3-совместимом бакете. Переменные администратора необходимы каждой миграции; изменение пароля в `.env` не меняет пароль существующего администратора. Перед использованием существующих volumes с закреплёнными версиями PostgreSQL, RabbitMQ и Redis проверьте совместимость версий и создайте проверенную резервную копию: автоматический откат данных к более старой версии не предусмотрен.

Сервер приложения привязан к `127.0.0.1:HTTP_PORT`. Для доступа извне нужен отдельно настроенный HTTPS reverse proxy; настройка домена, TLS и прокси не входит в этот workflow. Укажите в `TRUSTED_PROXIES` только проверенные адреса прокси. Не публикуйте порты PostgreSQL, Redis и RabbitMQ.

## Настройки GitHub

Для environment `production` или репозитория задайте secrets:

* `DEPLOY_HOST`, `DEPLOY_USER` — SSH-хост и пользователь; порт SSH 22.
* `DEPLOY_SSH_KEY` — приватный ключ пользователя деплоя без интерактивной парольной фразы.
* `DEPLOY_KNOWN_HOSTS` — проверенная строка host key из `known_hosts`. Сверьте её отпечаток с сервером по доверенному каналу до добавления.
* `GHCR_READ_USER`, `GHCR_READ_TOKEN` — учётная запись и токен для чтения production-образа из GHCR. Для приватного пакета права на пакет и `read:packages` должны быть настроены отдельно; пакет должен быть доступен этой учётной записи.

В серверном `.env` также укажите надёжный `GRAFANA_ADMIN_PASSWORD`; при отсутствии значения production Compose не запустится. Для Telegram-алертов задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Grafana и Prometheus слушают только localhost; для удалённого доступа используйте защищённый прокси или SSH-туннель. Настройка, ограничения и пороги описаны в [OBSERVABILITY.md](OBSERVABILITY.md).

Задайте variable `DEPLOY_DIR` — абсолютный путь к каталогу сервера, например `/srv/snap-flow`. Создайте environment `production`, если он поддерживается настройками репозитория. Выдайте GitHub Actions право публиковать пакеты GHCR. Серверу нужны исходящий доступ к GHCR и доступ к S3 и SMTP. Токен чтения GHCR сохраняется Docker на сервере после login; ограничьте его права и защитите Docker config.

## Процесс и ограничения

После успешных проверок GitHub собирает и публикует образ, помеченный SHA коммита. Deploy загружает конфигурацию в `releases/<SHA>`, скачивает образы, поднимает зависимости, запускает миграции и обновляет процессы. После проверки Docker записывает `current-image` и `current-release`. Сервер использует отдельный постоянный `.env`, он не отправляется из GitHub.

Деплой допускает короткий простой. После успешной миграции при ошибке запуска приложения или мониторинга скрипт пытается вернуть контейнеры предыдущего релиза; при первой установке предыдущего релиза может не быть. Схема базы автоматически не откатывается, поэтому миграции и формат данных должны оставаться совместимыми с предыдущим приложением. `/` проверяет только ответ HTTP-сервера, а не полную работоспособность S3, почты и очередей. Протестируйте процесс на отдельном сервере и проверьте восстановление PostgreSQL и S3 из резервных копий до работы с реальными данными.

Для новых объектов нужен отдельный STORAGE_ENCRYPTION_KEY и его STORAGE_ENCRYPTION_KEY_VERSION. Для старых S3-объектов сохраните прежнее значение TWS_SECRET_ACCESS_KEY в STORAGE_LEGACY_ENCRYPTION_KEY до смены доступа к S3. Предыдущие версионированные ключи указываются в STORAGE_PREVIOUS_ENCRYPTION_KEYS как JSON-объект. Храните ключи вместе с резервными копиями. Старые версии приложения не умеют читать новый формат: откат к ним после записи новых объектов небезопасен. Миграции должны оставаться совместимыми со старым релизом; автоматический откат схемы не выполняется.

Для первого обновления со старого релиза включите STORAGE_WRITE_LEGACY=true и задайте STORAGE_LEGACY_ENCRYPTION_KEY: новые записи сохранят старый формат, который прежний релиз может читать. После успешного обновления всех процессов и подтверждения возможности отката разверните следующий релиз с STORAGE_WRITE_LEGACY=false: теперь предыдущий релиз уже поддерживает чтение нового формата. Без этого двухэтапного перехода автоматический откат к первоначальному релизу после записи новых объектов небезопасен. Автоматическое перешифрование старых файлов не выполняется.
